# Reviewable hosted connector core

This change provides library adapters, not a deployed/public connector. `http.ts` creates the HTTPS-origin resource/authorization app with stateless Streamable HTTP at `/mcp`. `oauth.ts` supplies connector Authorization Code + S256 PKCE, short-lived opaque tokens, selected-board grants and revocation. The SDK validates PKCE before exchanging the single-use code. Use only predefined public clients with the exact client ID and callback obtained from the ChatGPT/Codex connection setup; metadata does not advertise DCR or CIMD. No URL-provided client metadata is fetched. Refresh grants are deliberately disabled; access tokens last 15 minutes and require reconnection after expiry.

`SqlOAuthStore` persists hashed code/token keys and opaque grants using a dedicated SQL executor. Its `take` is an atomic DELETE RETURNING. The private-schema migration is prepared for review. Provision a dedicated backend DB role and backend-only RLS policy; never grant this schema to anon/authenticated or expose it through the Data API. Schedule expired-record cleanup. Sessions live in a separate encrypted credential vault, not in model inputs/results or the OAuth-records table.

`hostedAccountResolver` takes a vault callback that loads/refreshes the user's existing Supabase session, validates it through getUser, and creates a new publishable-key/RLS client for every request. It never reads local credentials or shares a Supabase client between requests. It preserves the existing Supabase user and subscription. The connector token is opaque and bound to its issuing store, canonical resource and registered client. Tokens are never forwarded to Supabase; the user's server-held account session supplies the RLS JWT.

## Wiring required before production

1. Host behind TLS at the configured canonical origin and preserve its Host header. Configure actual allowed browser Origins. Add edge request limits and OpenAI client mTLS validation where appropriate.
2. Mount ZeroBoard's authenticated consent UI at `consentUrl`. Show the requesting client, exact scopes and selected board names; give the user Allow/Cancel controls. The `request` value is only a pending OAuth reference, not a login credential. Authenticate with the existing Supabase account. Never trust an input user ID or matching email as proof of identity.
3. Add an authenticated, CSRF-protected backend consent handler. Obtain `accountRef` exclusively from the server-held session. Call `consentRequest` to render scopes and `approveConsent` only after explicit user consent. Redirect to the returned exact callback. Do not expose approveConsent directly as an unauthenticated route. Cancel must discard the pending request or let it expire; no tokens are issued. The app's consent UI/session-vault adapters are not implemented in this first milestone.
4. Provide the durable SQL executor and encrypted vault callback, then construct ZeroBoardOAuth and createHostedApp with a stable >=32-byte proposal secret. Keep secrets in server configuration. The secret binds previews to the authenticated account and selected-board set; changing it invalidates outstanding previews.
5. Show connections in ZeroBoard account settings and call revokeConnection with the authenticated user ID. `/revoke` already revokes the whole grant for a token held by its registered OAuth client. Recheck session revocation in the vault; Supabase JWT lifetime alone is not immediate session-revocation enforcement.
6. Inspect deployed policies for extra permissive UPDATE policies before applying the editor-enforcement migration. Repository evidence does not establish deployed RLS. Apply migrations to disposable/staging Supabase and run its advisors/full schema tests. Existing boards.data optimistic checks protect MCP writes, but web clients can still overwrite newer data with stale unconditional writes.

The initial public scope is `boards:read` and `cards:add`. Reads require explicit ownership/membership plus selected-board inclusion; public/embed visibility alone is insufficient. Viewers can receive read grants, and write grants require owner/editor access at consent and at mutation. Plugin mode omits destructive and existing-card edits, board creation and generate_board. Local legacy mode remains available with stricter membership/editor enforcement.

Meeting commit requires an unmodified signed preview, unchanged board revision, current edit access and explicit approval. `approved=true` is not a human-authentication mechanism: host tool approval and the skill's explicit preview approval are required. Each batch writes cards and calendar dates atomically into JSONB. Stable IDs prevent duplicate batches while the preview is valid. Ambiguous network failures are not automatically replayed. A deleted or partially removed batch requires review/re-preview; host workflows must inspect the board before retries.
